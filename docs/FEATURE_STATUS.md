|---|---|
| User accounts and ECHO profiles | Implemented, not end-to-end verified |
| Persistent memories and public/private visibility | Implemented, needs authorization tests |
| Shared rooms with authenticated access | Implemented; single-process real-time state |
| AI dialogue | Provider-backed, needs configured key and cost controls |
| Unified avatar provider discovery | Implemented for Tavus, LiveAvatar, and the independent local 3D renderer. The local renderer remains usable without provider credentials or Copilot MCP; its preview/import capabilities are not represented as a managed live-conversation session. |
| Humanlike 3D avatar | Skinned stylized starter GLB; not photorealistic; commercial asset license not yet verified |
| User likeness generation | Optional Avatar SDK photo-to-rigged-GLB flow; LiveAvatar Alpha image-avatar upload with explicit consent. No documented video-upload creation endpoint |
| Photorealistic video avatar | HeyGen LiveAvatar API/SDK integration implemented: provider catalogue, selection, session token/start/stop, FULL and LITE paths. External live video delivery still requires a real provider session |
| Provider-driven speech/video synchronization | LiveAvatar FULL uses its managed voice pipeline; LITE sends microphone PCM to avatar video. No local volume-only mouth animation is used for provider video |
| Tavus video avatar | Tavus conversation creation and official Daily-backed WebRTC UI are integrated, with provider faces, remote-video readiness, session status, transport diagnostics, and PAL default-face fallback. A configured PAL and an intentionally started provider session are required to verify live media |
| Native meeting bot integrations | Not implemented |
| ECHO World voice | Direct WebRTC mesh for authorized immersive room participants; no TURN relay or spatial audio |
| Subscription charging | Not implemented |

## Avatar voice and LiveAvatar controls

- **Video avatars:** The FastAPI backend keeps `LIVEAVATAR_API_KEY` private, validates provider authentication, retrieves public/account avatars and creates user-scoped sessions. The Next.js Pages Router uses the official `@heygen/liveavatar-web-sdk` for FULL and LiveKit/WebSocket media for LITE. Users can preview provider media, select/save avatars, and switch between available avatars. Provider authentication is not proof of a real session stream; live video delivery requires a successful external provider session and has not been asserted unless actually observed.
- **Configured library:** All six `LIVEAVATAR_AVATAR_n_ID`, `_VOICE_ID`, and `_MODEL` settings are associated by slot and passed to the backend. Unsupported managed LLM models are rejected. `LIVEAVATAR_DEFAULT_AVATAR_ID` remains only the fallback when the user has not selected an avatar. The Wayne sandbox avatar is the only supported avatar while `LIVEAVATAR_SANDBOX=true`; configured avatars require a deliberate switch to production mode and consume provider credits.
- **FULL mode — Let ECHO Speak:** LiveAvatar manages microphone speech recognition, conversation, TTS, and avatar video. The mode is disclosed as AI-operated and uses provider voice, not the user's voice. An ECHO profile is sent only after explicit per-session authorization; its public knowledge is included, and private knowledge has an independent opt-in. ECHO caches the reusable provider context ID and stores the context/knowledge scope and consent timestamp in PostgreSQL. Migration `0009_liveavatar_consent` adds this metadata.
- **LITE mode — Speak as my avatar:** The browser captures the selected microphone with echo cancellation, noise suppression, and automatic gain control, resamples to 24 kHz mono signed PCM, and streams provider-documented chunks over the LiveAvatar audio-control WebSocket. The original voice is preserved and provider video is synchronized to supplied audio. This is microphone passthrough, not STT/LLM/TTS or an AI conversation. A 600 ms initial chunk and subsequent 1 s chunks are used; audio-control reconnect attempts are bounded.
- **Audio lifecycle:** Microphone device selection, mute, provider keep-alive, session ownership checks, start/stop/closed status, a five-creation-per-minute user rate limit, and provider usage/credit retrieval are implemented. Failed LITE startup attempts are stopped and recorded, and photo/persona consent scopes and timestamps are persisted.
- **Tavus — Let ECHO Speak:** Tavus conversations use the provider conversation URL with the official `@daily-co/daily-react`/Daily WebRTC components. The browser requests microphone permission before joining and passes that microphone track to the call; Daily transport network state, loss, jitter and RTT are shown while connected, and remote video is marked ready only after its provider track is playable. The backend retains Tavus API credentials, validates configured faces against the provider, checks PAL access, and provides owner-checked session state. Tavus Full-Pipeline speech is provider-operated; it does not preserve the user's raw microphone voice as avatar speech.
- **Tavus — audio reliability:** ECHO reports observable WebRTC transport diagnostics rather than claiming to control Tavus PAL turn-taking or recovery behavior. Firefox may not expose send-side loss, jitter, or RTT. This frontend joins/leaves the provider room cleanly; reconnect policy and conversation recovery remain subject to Tavus/Daily's supported behavior and are not represented as a custom guaranteed recovery service.
- **Tavus library:** Up to eight configured `TAVUS_AVATAR_n_ID`/`TAVUS_AVATAR_n_NAME` slots are prioritized when the provider reports those faces as completed and available; other eligible provider faces are included dynamically. Provider thumbnails and preview media are shown when returned. PAL access, plan, and face availability are account-controlled.
- **Tavus personalized media:** Consent-gated face and voice creation routes are wired to the provider APIs and ownership/status records. Studio accepts public HTTPS URLs for image/video/audio training and polls provider state; it does not host or upload media. Image-trained faces require a provider stock voice name or an ECHO-owned Tavus voice ID. Video-trained faces use the video's audio. Provider permissions, model availability, identity checks and plan limits remain external. Training and attaching a custom voice to the configured PAL have not been verified in a live conversation.
- **LiveAvatar personalized avatars:** LiveAvatar's documented creation endpoint is Alpha image upload. It accepts a still JPEG/PNG, not a recording; webcam capture submits one still frame. The UI states likeness permission requirements and plan restrictions. Avatar SDK remains optional for 3D GLB generation only.
- **Avatar SDK/3D:** Avatar Studio and ECHO World retain an optional skinned GLB viewer/import path. WebGL 2 is required only for this 3D viewer, not for LiveAvatar video. The starter GLB is not photorealistic, and its volume-based movement is not represented as provider lip sync.
- **External meetings:** No system camera device or autonomous conference participant is created by the browser or LiveAvatar SDK. Ubuntu needs a host-level OBS/v4l2loopback or equivalent bridge to expose captured provider video to Meet/Zoom/Teams; mic/video synchronization through that bridge is not end-to-end verified. Digital-avatar and AI operation should be disclosed to meeting participants.

Do not market a provider-authenticated account, built frontend, or selected avatar as a verified live session. Video upload creation, voice cloning, OS camera export, and external meeting attendance remain blocked by provider support and/or host infrastructure. Tavus live streaming remains unverified until the configured PAL successfully starts and remote audio/video are observed.

Do not market unimplemented features as available. Tavus face/voice training UI and backend routes are implemented, but generation completion and live use require an authorized provider account and were not live-tested here. A functioning commercial release requires provider integration, verified consent, security and performance tests, billing, and operational readiness.
